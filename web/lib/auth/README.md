# Supabase browser authentication

`client.ts` creates the browser singleton with PKCE, SDK-owned persistence and automatic refresh. Application state holds only the user ID and readiness. The API client reads the SDK session before requests; application code never copies tokens into its own storage.

Registration collects name, email, password, confirmation and explicit age consent. During the temporary pilot, `NEXT_PUBLIC_AUTH_REQUIRE_EMAIL_CONFIRMATION` defaults to false and Supabase **Confirm email must be off**. Registration uses a separate SDK client with a unique storage key, no persistence/refresh/URL detection, and the implicit signup flow required for autoconfirm. It disposes that client after the response; the issued session is never copied into application state or browser storage. Success routes to `/sign-in?registered=1` with an account-created notice. Only an explicit password sign-in starts the persistent app session and profile/farm setup. The registration name only suggests a public display name the farmer confirms later.

Returning users use `signInWithPassword`. No social providers or passwordless sign-in buttons are exposed. Existing unconfirmed accounts need explicit admin activation before password sign-in; disabling confirmation does not activate those earlier records. The email-verification UI remains gated behind `NEXT_PUBLIC_AUTH_REQUIRE_EMAIL_CONFIRMATION=true`, which must be coordinated with the hosted Confirm email setting. Password recovery retains its 60-second UI cooldown and still depends on email delivery. Future code verification is not implemented by this flag.

Forgot password uses `resetPasswordForEmail` with the same allowed callback URL. The SDK’s `PASSWORD_RECOVERY` event routes to `/auth/reset-password`, where `updateUser` saves the new password. Both new-password fields require matching values and at least eight characters; Supabase remains authoritative for password policy. Existing users can sign in with older passwords without being blocked by the new-password minimum.

Configure `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_AUTH_REQUIRE_EMAIL_CONFIRMATION=false` and the deployed `/auth/callback` redirect allowlist. The redirect always uses the current origin. Changing local files does not update Vercel or Supabase. Set the public flag for the Vercel build and turn off Confirm email in the Supabase dashboard. If Supabase still requires confirmation, registration reports an activation error instead of promising immediate password sign-in.

Authentication requires connectivity. Forms keep credentials only in memory and clear passwords after successful submission. Profile/farm drafts are account-scoped and local-first. Sign-out clears drafts and SDK session data, asking before discarding unsynced work.

Browser tests mock Supabase transport with synthetic credentials and exercise registration-to-login, session isolation, provider-setting mismatch, password login, recovery, provider failures and offline handling. They never send real emails. Live password sign-in needs a test account; recovery delivery still needs a supplied address. Never commit email links, tokens or storage dumps.
